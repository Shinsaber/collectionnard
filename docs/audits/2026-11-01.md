## 1. Synthèse

Le projet est sain : la CI est entièrement verte (gofmt, vet, golangci-lint, 252 tests Vitest, build), govulncheck ne
trouve aucune vulnérabilité atteinte, les 26 avis `npm audit` sont tous faibles ou modérés et confinés à l'outillage

Un seul constat **haut** : la génération de vignettes décode des images jusqu'à 50 Mpx sans borne de concurrence, ce qui
permet à un membre invité d'épuiser la mémoire du serveur. Trois autres points de sécurité méritent un lot rapide : le
limiteur de débit par IP devient global derrière le reverse-proxy TLS que la documentation impose, les jetons de partage
et d'invitation passent en query string dans les journaux nginx, et aucun quota ne borne les envois d'images d'un compte.
Côté qualité, les deux listes non paginées (`/items/{id}/relations`, `/tags`), Element Plus chargé en entier dans le
chunk d'entrée, six routes sans test de handler et la duplication des connecteurs BnF forment un second lot. La
conformité aux conventions est bonne ; l'écart principal est que sept codes d'erreur des comptes (P4-0) sont traduits par
le front sans figurer dans `api/openapi.yaml`.

## 4. Sécurité

### S-001 — Vignettes : décodage jusqu'à 50 Mpx sans borne de concurrence — haute — constaté

**Où** : [handler/thumbnail.go:26](../../server/internal/handler/thumbnail.go#L26) (cap `maxThumbSourcePixels`),
[thumbnail.go:40-61](../../server/internal/handler/thumbnail.go#L40-L61) (`serveThumbnail`, aucune sémaphore),
[thumbnail.go:79](../../server/internal/handler/thumbnail.go#L79) (`image.Decode` complet) ; route publique
[handler/handler.go:75-95](../../server/internal/handler/handler.go#L75-L95) ; envoi ouvert à tout compte
[handler.go:125](../../server/internal/handler/handler.go#L125).
**Constat** : la vignette `?w=240` est générée à la première demande, sans authentification, sans limite du nombre de
générations simultanées ; le seul garde-fou est 50 Mpx par image. Un PNG uni de 7 000 × 7 000 px pèse quelques dizaines
de ko (loin de `MAX_UPLOAD_SIZE`) mais se décode en ~200 Mio (NRGBA), puis passe dans `draw.CatmullRom.Scale`. Tout compte
connecté peut envoyer de nombreux fichiers de ce type (contenus distincts donc noms distincts) et demander leurs vignettes
en parallèle, même anonymement. Atténuations : il faut un compte invité ; une vignette n'est calculée qu'une fois par image.
**Impact** : quelques requêtes concurrentes suffisent à dépasser la mémoire d'un petit serveur et à faire tuer le conteneur
`server` (aucune limite mémoire dans les compose) ; `restart: unless-stopped` relance, l'attaque est rejouable.
**Correctif** : sémaphore global (canal bufferisé à 2) autour de `writeThumbnail`, servir l'original ou répondre 503 au-delà ;
abaisser le cap à ~25 Mpx ; en option, lire `image.DecodeConfig` à l'envoi (`UploadFile`) et refuser les images au-delà du
cap plutôt que de les stocker. Effort : petit.
**Vérification** : test dans `thumbnail_test.go` lançant N requêtes concurrentes sur de grands PNG et vérifiant qu'au plus
deux décodages sont en vol (compteur atomique injecté) ; RSS stable sur 10 requêtes parallèles.

### S-002 — Limiteur `/auth/*` par IP inopérant derrière un reverse-proxy — moyenne — constaté

**Où** : [web/nginx.conf:43](../../web/nginx.conf#L43) (et 54, 65, 76, 85 : `proxy_set_header X-Real-IP $remote_addr`,
aucune directive `real_ip_header` / `set_real_ip_from`), [middleware/realip.go:17](../../server/internal/middleware/realip.go#L17)
(seul `X-Real-IP` est lu), [docker-compose.prod.yml:11-12](../../docker-compose.prod.yml#L11-L12) et
[README.md:158-160](../../README.md#L158-L160) (« placer devant un reverse-proxy qui termine TLS »),
[handler/handler.go:64-73](../../server/internal/handler/handler.go#L64-L73) (un seul compteur pour login, refresh,
logout, invitation, register, reset-password).
**Constat** : derrière le reverse-proxy TLS que la documentation impose, `$remote_addr` vu par nginx est l'adresse du
proxy ; `X-Real-IP` vaut toujours la même valeur et le limiteur (10/min) devient global à l'instance. Le compteur est
partagé avec `/auth/refresh`, appelé par chaque appareil toutes les 15 minutes.
**Impact** : un client anonyme peut, avec 10 requêtes par minute, bloquer connexion et rafraîchissement pour tous (429) ;
sans attaque, une vingtaine d'appareils actifs se gênent. À l'inverse, le limiteur ne protège plus du bourrage
d'identifiants ciblé.
**Correctif** : dans `web/nginx.conf`, `set_real_ip_from <réseau du proxy>; real_ip_header X-Forwarded-For;
real_ip_recursive on;` (fichier inclus optionnel ou variable d'environnement, documenté dans le README « Mise en
production ») ; séparer le compteur de `/auth/refresh` (ou le clef par jeton) de celui de `/auth/login`. Effort : petit à moyen.
**Vérification** : derrière un proxy de test, `docker compose logs server` montre des `ip` distinctes pour deux clients ;
test de `ratelimit_test.go` : 10 connexions d'une IP ne bloquent pas le rafraîchissement d'une autre.

### S-003 — Jetons de partage et d'invitation en query string dans les journaux nginx — moyenne — constaté (absence de directive) / supposé (format par défaut de l'image)

**Où** : [handler/sharing.go:132](../../server/internal/handler/sharing.go#L132) (`/share?token=`),
[handler/account.go:73](../../server/internal/handler/account.go#L73) (`/auth/invitation?token=`),
[web/nginx.conf](../../web/nginx.conf) (aucune directive `access_log` ni `log_format`), [web/Dockerfile:19](../../web/Dockerfile#L19)
(`nginxinc/nginx-unprivileged`, dont la configuration `http` par défaut journalise `$request` complet sur stdout).
**Constat** : le serveur Go ne journalise que `r.URL.Path` ([middleware/logger.go:30](../../server/internal/middleware/logger.go#L30),
correct), mais nginx écrit l'URI complète, requête incluse, dans `docker logs` du service `web`. La base ne garde que des
hachés ; le journal nginx annule cette précaution pour les liens de partage (valables jusqu'à révocation) et les
invitations (7 jours).
**Impact** : quiconque lit la sortie du conteneur `web` (collecteur de journaux compris) peut rejouer un lien de partage ou
consommer une invitation en attente.
**Correctif** : `log_format colec '$remote_addr [$time_local] "$request_method $uri" $status …'` (avec `$uri`, pas
`$request`) et `access_log /dev/stdout colec;` dans le bloc `server` de `web/nginx.conf` ; à défaut un `map $request_uri`
qui masque `token=`. Effort : petit.
**Vérification** : `curl 'http://localhost:3000/api/v1/share?token=abc'` puis `docker compose logs web | grep abc` vide.

### S-004 — Aucun quota d'envoi d'images par compte — moyenne — constaté

**Où** : [handler/upload.go:28-90](../../server/internal/handler/upload.go#L28-L90) (aucun compte ni plafond par
utilisateur), [handler/upload_purge.go:16](../../server/internal/handler/upload_purge.go#L16) et
[:22](../../server/internal/handler/upload_purge.go#L22) (purge manuelle, admin, délai de grâce 24 h),
[docker-compose.yml:56](../../docker-compose.yml#L56) (volume `uploads` sans limite).
**Constat** : tout compte connecté peut envoyer un nombre illimité de fichiers de 10 Mio (dédoublonnés par hachage de
contenu seulement) ; rien ne les rattache à leur auteur et la purge ne s'exécute que si un admin la lance, jamais avant 24 h.
**Impact** : saturation du volume `uploads` (et du disque hôte) en quelques minutes par un membre ; les envois légitimes
et PostgreSQL (si même disque) échouent ensuite.
**Correctif** : compteur en mémoire par utilisateur et par heure (octets et fichiers) dans `UploadFile` → 429, ou table
`uploads (name, user_id, size, created_at)` ; purge automatique périodique (goroutine comme `purgeRefreshTokens`,
[main.go:153](../../server/main.go#L153)) en plus du bouton admin. Effort : moyen.
**Vérification** : test de handler : le 21e envoi d'un même utilisateur dans l'heure répond 429 ; `df` stable après une rafale.

### S-005 — Jetons d'accès et de rafraîchissement en `localStorage` — basse — constaté

**Où** : [web/src/api/tokens.ts:1-30](../../web/src/api/tokens.ts#L1-L30), [web/src/api/client.ts:102-107](../../web/src/api/client.ts#L102-L107).
**Constat** : les deux jetons sont lisibles par tout script exécuté dans l'origine. La CSP
([nginx-security-headers.conf:11](../../web/nginx-security-headers.conf#L11), `script-src 'self' 'wasm-unsafe-eval'`, sans
`unsafe-inline`), l'absence de `v-html` et le filtrage des liens (`lib/schema.ts` n'accepte que http(s)) réduisent fortement
la surface XSS ; c'est un compromis classique, non documenté.
**Impact** : en cas de XSS, vol d'une session de 30 jours (refresh) plutôt que de 15 minutes.
**Correctif** : consigner la décision dans `docs/conception.md` ; durcissement possible plus tard : refresh token en cookie
`HttpOnly; SameSite=Strict` posé par `/auth/login` et lu par `/auth/refresh` (effort gros). Effort : petit (documentation).
**Vérification** : paragraphe dans la documentation.

### S-006 — Images publiques en cache un an, photos d'exemplaires comprises — basse — constaté

**Où** : [handler/handler.go:75-95](../../server/internal/handler/handler.go#L75-L95) (route publique),
[web/nginx.conf:51](../../web/nginx.conf#L51) (`Cache-Control: public, max-age=31536000, immutable`),
[docs/phases/social.md:22](../phases/social.md#L22) (« noms non devinables : rien à changer »).
**Constat** : la protection repose sur le nom (SHA-256 du contenu). Une URL connue (page publique un temps, lien de partage
révoqué, journal, capture) reste valable tant que l'image n'est pas purgée, et les caches intermédiaires peuvent la garder un
an. Les photos de l'état d'un exemplaire (lot M5) sont des données personnelles, pas du catalogue.
**Impact** : fuite résiduelle, non révocable, d'images de collections repassées en privé.
**Correctif** : documenter la limite (aide de la galerie d'exemplaire, `docs/phases/mobile.md`) ; option future : servir
les galeries des `collection_items` par une route authentifiée (`fetch` + `blob:` déjà permis par la CSP) ou en
`Cache-Control: private`. Effort : petit (documentation) / moyen (route dédiée).
**Vérification** : phrase dans la documentation ; sinon test de handler 401 sans jeton sur la nouvelle route.

### S-007 — Hygiène du dépôt et de la chaîne d'approvisionnement — basse — constaté

**Où** : [.gitignore:14-15](../../.gitignore#L14-L15) (`.env`, `.env.local` seulement), [.env.example:5](../../.env.example#L5)
(`POSTGRES_PASSWORD=colec`), [.github/workflows/ci.yml:17](../../.github/workflows/ci.yml#L17) (actions épinglées par tag
majeur, pas par SHA), [server/Dockerfile:20](../../server/Dockerfile#L20) + [server/main.go:50](../../server/main.go#L50)
(seeds et sous-commande `seed` embarqués dans l'image de production).
**Constat** : rien n'est exploitable seul (aucun secret jamais commité : `git log --diff-filter=A -- .env .env.*` ne renvoie
que `.env.example` ; le `JWT_SECRET` de [flake.nix:61](../../flake.nix#L61) est une valeur de dev explicite), mais ce sont des
portes classiques : un `.env.production` serait commité ; le mot de passe PostgreSQL d'exemple peut être gardé tel quel ;
une action ou une image substituée en amont passerait ; `colec-server seed` lancé par erreur en production crée `admin/admin`.
**Correctif** : `.env*` + `!.env.example` dans `.gitignore` ; `POSTGRES_PASSWORD=` vide avec le même conseil `openssl rand`

`seed` quand `SEED_ON_EMPTY` n'est pas `true`, ou retirer les seeds de l'image prod. Effort : petit.
**Vérification** : `git check-ignore .env.production` ; `grep -c '@[0-9a-f]\{40\}' .github/workflows/ci.yml` ;

  dans le dépôt.
- Aucune exécution : ni test de charge des vignettes (S-001), ni mesure RSS, ni plan d'exécution SQL (Q-001, Q-006) ; la
  composition des chunks (Q-002) vient d'un `grep` sur `web/dist/`, sans analyseur de bundle.
- `store/export.go` (773 lignes) et `connectors/plan.go` (494) lus par recherche ciblée, pas ligne à ligne ; les connecteurs
  comparés sur la recherche d'éditions et le rattachement à l'œuvre seulement.

  rendu ; miroir `types.ts` ↔ `model` vérifié sur cinq structs ; `docs/domaines/*.md` ↔ paquets sondé sur un type (`Volume`).
- Clés i18n orphelines (Q-007) détectées par heuristique puis confirmées à la main ; les clés manquantes n'ont pas été
  recherchées (le compilateur et `i18n.test.ts` les couvrent partiellement).
- Langue des commentaires Go (mélange anglais / français) et libellés des objets imbriqués (`external_ids.wikidata`) : aucune
